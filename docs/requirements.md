# 需求追踪：从「检索问答」到「可治理的工单 Agent」

目标：只做检索 RAG 已经不够，面试官要看到的是**工具调用 + 权限与审计 + 可恢复 + 可观测 + 评估**。本表把功能清单（A 咨询与检索 / B 查询与执行 / C 治理与安全 / D 观测与评测）逐项对照现状，说明做不做、怎么改造、怎么验收、谁来做。

## 先说明三处和我们场景不匹配的地方

清单是按「硬件售后」写的（型号、购买日期、保修到期、物流）。我们的领域是 **ERP 软件的售后**，客户是使用 ERP 的商家，知识库没有型号/保修/生效日期这些字段。所以：

- **A2 的「型号 / 生效日期」不做**，改成「产品线（企业版/极速版/供销平台…）」过滤。生效日期只有版本日志有，且通知类文档的标题只有月日没有年份，没法可靠过滤。陷阱题改用真实素材：企业版和极速版里有 **67 组同名但内容不同的文档**（含版本日志，需剔除），客户明说「极速版」时必须引用极速版的文档。
- **B2「查订单：购买日期、保修到期」改成**查商家的电商订单（状态、金额、买家手机号脱敏）和店铺授权状态；**B3 查物流**保留。这些后台系统用**合成数据**的沙箱，文档和报告里都会写明。
- **D2 成本统计要「实测 token × 当前单价」**：网关的 `/api/pricing` 返回的价格是模糊的（`model_ratio: 0`），拿不到单价。所以单价做成需要你填写的配置，必须写来源和日期；没填时报告只给 token 数，**不编价格**。

## 不做 / 不承诺

- 不做完整的聊天前端，只做 trace 查看器和一个简单的工单队列页。
- 沙箱数据是合成的，**不能说成对接了真实系统**。
- 角色用 header 模拟，**不是真正的认证**；讲的时候要说清楚。
- C5 在 Windows 上用 `Popen.kill()`（TerminateProcess，等价于不可捕获的强杀），不是 Linux 的 `kill -9`；原理相同，但不是同一个系统调用。

## 分工依据（来自这个项目里它们各自的实际表现）

| 谁 | 观察到的表现 | 这次给它的任务 |
|---|---|---|
| Codex | 检索层最扎实：路径穿越、索引校验、变异测试都做了；但慢、重 | **网关内核**（C2/C3/C4/C5/C6、B5/B6 批准流程）：正确性要求最高、并发和崩溃恢复最容易写错 |

| DeepSeek Harness | 测试写得扎实、会做变异验证；沙箱里不能提交 git、不能用 uv，由我代提交；它的抽取规则噪声偏大 | **业务沙箱**和**测试语料**（脱敏、超时降级、注入文档、陷阱题、工具选择集） |
| Claude（我） | 接口设计、提示词、真实模型评估、集成 | 冻结接口、图的改造（多轮、查询代理、结构性防注入）、API 接入、评估 |

**花费控制**
1. 能用确定性代码的地方不调模型：网关、幂等、审计、状态机、脱敏、交接摘要都没有模型调用，测试全部用假模型。
2. worker 只做自包含模块，**由我集成**，避免它们同时改图和 API 造成返工。
3. 真实模型评估只在我这边跑，沿用现有评估集和缓存，用 `--quick` 档做日常回归。
4. 谁买单：opencode 走的是**你的网关额度**，和我的评估共用；Codex 和 DeepSeek Harness 各自的账户我看不到花费。
