状态：✅ 已验证达标｜◐ 部分达标或有保留｜✗ 未达标或未做。每一项都写了依据（测试名或评测数字）和**没有覆盖到的地方**。

## 真实服务端到端走查（真实模型 + 真实知识库 + 真实工单存储与网关）

起一个 `create_app(governed=True)` 的服务，用 8 张工单走完整流程。验证到的行为：
- 笼统消息追问；查自己的订单（含物流）→ 工具结果进审核卡、引用是"系统查询结果"；查**别家店铺订单**和**不存在的订单**拿到**逐字相同**的回复；按店铺名查授权；需查账单 → 升级。
- 坐席批准后客户**还看不到任何回复**，确认后才发出，**重复确认 3 次客户仍只收到 1 条**，工单变 `resolved`。
- 升级后 `/handoff` 给出原因（含转交团队）、已执行动作、客户最后一句话。
- 越权：客户看他人工单 403、客户调审计 403、客户确认发送 403、别的坐席确认他人待发送 403、对已被他人负责且不在待审核的工单再审核 409。
- 这次走查**发现并修了一个真缺陷**：「我的店铺有问题」被追问"请补充电商平台名称"，答了平台之后系统仍不知道问题是什么；现在笼统消息优先问"具体遇到什么问题"（有回归测试）。
- 同一轮里我自己的脚本把"a2 审核了 a1 的工单返回 200"当成越权，查证后是脚本假设错了（那张工单从没被 a1 认领，a2 是第一个审核的所以自动认领）；用 a1 真的认领了的工单重测，结果符合预期。
- 真实 trace：8 份 JSON，每个 LLM 调用都带网关返回的 token（`usage_missing` 0 次）。`human_review` 在时间线里出现两次——一次进入等待、一次审核后恢复，这是 LangGraph `interrupt` 的真实行为（节点会重新执行），不是 bug，但看 trace 的人会困惑。
- **单次 LLM 调用耗时 p50 7.7 秒、最大 20 秒**，远高于之前评估里的整单 3.2 秒。这是当时网关的负载，所以文档里其他地方的耗时数字对"网关繁忙"没有代表性。

## 工具选择评测（D3 的一部分）

- 60 条模板生成。第一次真实运行：**明确+歧义混在一起 tool_accuracy 0.883（53/60）**。
- 7 个"错误"全是歧义问法（"看下发货了没"，查订单或查物流都说得通），模型选了 `query_shipment`。我**在看到结果之后**把这些问法改成"两个工具都可接受"并单独统计。所以改后的**明确问法 52/52、参数 100%、越权 6/6、泄露 0** 里，工具选择的 100% 不是独立准确率；越权和泄露的结果不受标签改动影响。
- 它同时暴露了一个真实缺口：客户说的是店铺名而不是编号，已补上"店铺名→编号"的解析（只在调用者自己的店铺范围里找，别家店铺与不存在不可区分）。
