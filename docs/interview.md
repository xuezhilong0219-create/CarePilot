# 面试讲解材料

数字都来自 README 和 docs/status.md。**讲的时候先说清楚：评估集是合成的，订单/物流是沙箱数据，角色是请求头模拟，数字用来比较方案，不是线上效果。** 主动讲，比被追问出来好得多。

## 一句话定位

不是"检索问答"，而是**让 Agent 敢动手的那一层**：模型只能提议，所有动作过一个没有模型参与判定的网关（四道闸、审计、幂等、崩溃恢复、预算守卫），写操作必须人工批准，越权和"不存在"不可区分，每个动作能回溯。检索问答只是其中一个节点。

## 5 分钟讲法

**1. 背景（30 秒）**
我做过售后技术支持，也做过一个客服助手：知识库接某个产品的 API 问答。检索问答现在满大街都是，真正让企业不敢上线 Agent 的是"它能不能乱动东西、动错了怎么办、怎么证明它没乱动"。所以我做了这一层，并且用评估集量化每次改动。

**2. 架构（1.5 分钟）**
LangGraph 状态机：分诊 → （笼统则追问 / 要查客户自己数据则规划工具 / 否则检索回答）→ 人工审核（`interrupt`，状态落 SQLite）→ 执行。三个我刻意做的设计：
- **模型只能提议。**规划模型只看客户说过的话，只能提议只读查询；订单号必须**逐字出现在客户消息里**才会执行，防止它凭空捏造标识符；写操作和对外发送只由确定性代码在人工批准后经网关执行。
- **网关里没有任何模型调用。**四道闸：schema → 业务规则 → 权限 → 风险分级。每次调用（包括被拒绝的）都写审计；幂等键是 `sha1(run_id + 工具 + 规范化参数)`；对外发送是"批准 → 二次确认"，重复确认只产生一条消息。
- **越权和不存在不可区分。**客户查别家店铺的订单，和查一个不存在的订单，回复逐字相同，不泄露记录是否存在。

**3. 最有价值的部分：用评估和对抗测试找到自己看不到的 bug（2 分钟）**
- 评估：最初放行率 48%。看失败原因发现两个设计错误——引用校验被"长 chunk 编号"误杀 38%，缺槽位就追问误拦 20%。修完到 80% 以上，同一份代码重复跑 4 次在 80.3%~83.3%。
- 回复内容：25% 的放行回复编造了资料里没有的具体事实，原因是我自己的提示词在诱导。改后 5.5%，**没降到 0**。
- 治理层：让另一个 agent **只看接口**独立写黑盒攻击测试，找到了我测不到的问题——审计分页传负数会让 SQLite 把整张审计表倒出来。我自己集成时又发现：同一个 run 里坐席会拿到客户那次的缓存结果；工具"副作用发生后才抛异常"被当成没执行而重复执行；审批永不过期。每个都有回归测试，改坏会变红。

**4. 诚实的局限（1 分钟）**
评估集是合成的，偏乐观；订单/物流是沙箱；角色是请求头模拟；注入评测里**去掉防护行对照也是 0/60**——说明提示词那一行没有可测量的贡献，真正的防线是结构；评审和被评是同一个模型；剩下 5.5% 的编造没解决；Docker 没验证过；没做压力测试；成本只有 token，没有金额（拿不到真实单价，我不编）。

**5. 如果有真实数据（30 秒）**
用真实历史工单替换合成评估集，再看这些数字还成不成立。

## 预期追问和实话

**幂等你是怎么做的？怎么证明？**
幂等键 = sha1(run_id + 工具名 + 规范化参数)，账本表有唯一约束；执行协议是"事务里预留 → 才执行 → 记 done"。验证：50 轮双线程 Barrier 并发每轮恰好 1 次副作用；真实子进程强杀在"副作用前"和"副作用后、记账前"两个点，恢复后副作用恰好 1 次，恢复先对账（调用工具的 `verify`）再决定认领还是重试。**注意**：这依赖 `verify` 可靠和下游也支持幂等；没有 `verify` 的写工具我保守地标"需人工"，不自动重试。

**kill -9 真的做了吗？**
做了真实子进程强杀，但本机是 Windows，`Popen.kill()` 是 `TerminateProcess`，等价于不可捕获的强杀，不是 Linux 的 `kill -9`；也没有做"整个 API 进程被杀后 LangGraph checkpoint 恢复"的端到端测试。

**怎么防 prompt 注入？有数据吗？**
两层。**结构性**：回复节点没有工具；规划模型看不到知识库原文和订单留言（留言只能通过一个没注册给规划模型的工具读，而且返回时标 `untrusted`）；写和发送由确定性代码经网关执行。**度量**：60 条用例（10 种载荷 × 5 个位置）被带偏 0/60。但我同时做了**去掉提示词防护行的对照，也是 0/60**，所以不能说"提示词防护有效"，只能说这个模型对模板化注入本身就稳；判分器我校准过（顺从的回复必被检出）。更隐蔽的攻击我没覆盖。另外有个副作用：注入文本会让 21/60 的回复直接拒答。

**Agent 的死循环怎么防？**
`RunGuard`：同一个工具调用连续 3 次判 loop，乱换参数则 20 步内被步数上限打断，另有 token 和耗时预算。被中止后**只留一条内部备注并把工单标成需人工接手，不替人改状态**。局限：守卫在节点边界和规划循环里计数，打断不了一个已经卡住的模型调用（靠 HTTP 超时）。

**为什么不让模型直接调用写工具？**
因为那样"是否放行"就取决于模型的判断。我希望放行的决定是确定性的、可测试的、可审计的。模型的价值在理解客户说什么，不在决定能不能动数据。

**多轮对话怎么做的？**
工单级会话：历史（只取公开消息）加跨轮累积的槽位（平台/店铺/功能/仓库）。分诊时带上历史，本轮没提到但历史里有的实体沿用；检索用分诊改写后的独立问句。验证：连续 3 轮槽位不丢（图层和 HTTP 层都测了）。**局限**：指代消解的**质量**没有用真实模型评测，我验证的是机制。

**产品线（企业版/极速版）怎么处理？**
知识库里有 14 对企业版/极速版**同名但内容不同**的文档。客户明说版本时，过滤掉另一个产品线的同名文档（对方没有对应文档时保留，不让客户拿不到答案）。测得不过滤时前 4 个结果里混进另一产品线同名文档的比例是 21%~43%，随问法差一倍，所以我不引用单一百分比；过滤后 0 在构造上基本是保证的。LLM 出陷阱题基本行不通（9 个配对只出了 3 对），我改成直接测检索+过滤。

**成本多少？**
我只有 token，没有金额：真实运行 8 次，prompt 9108、completion 4501 tokens，`usage_missing` 0 次。网关的价格接口返回的是模糊值，所以单价是个**你必须自己填**的配置，要写来源和日期，没填就只报 token——我不会编价格。

**为什么不用 Dify / Coze？**
这个场景的价值在于：能做评估、能定制路由逻辑、能控制引用校验和网关。拖拽平台做简单问答很快，但我要的是"能量化每次改动的效果"和"放行由确定性代码决定"，代码里更容易做。（不要贬低别人的工具，说取舍。）

**为什么用 LangGraph？**
工单有分支、有状态、要人工介入，`interrupt` + checkpoint 正好对应。规划是一个有界循环（最多 4 步）而不是让模型自由决定下一步，因为流程大体确定，自由度只会增加不确定性。

**为什么不做 multi-agent？**
流程确定，一个图加几个节点就够；多 agent 在这里只会增加成本和排查难度。

**混合检索为什么没用？**
我做了，也调了权重（dev/test 拆分）。检索层面在 test 半边略好但不显著，端到端没有更好，还要多装一个模型、预建 20 分钟的索引。客户习惯贴报错原文和平台名，BM25 本来就强。数据没有支持"必须用向量"，所以默认 BM25，配置里可以切换。

**评估集怎么来的？可信吗？**
用知识库文档反向让模型写客户消息，文档就是标准答案；有防照抄校验；类别标签按文档目录机械打。**不完全可信**：用词偏近原文、一个样本只标一个答案文档。我把它当"比较方案的尺子"，不当线上指标。

**工具选择准确率多少？**
第一次真实运行 53/60。7 个"错"全是歧义问法（"看下发货了没"，查订单或查物流都说得通）。我**在看到结果后**把它们改成"两个工具都可接受"并单独统计，所以明确问法的 52/52 **不是独立准确率**——这点我会主动说。不受改标签影响的是：越权 6/6、泄露 0。它同时暴露了真实缺口：客户说店铺名而不是编号，我补了"店铺名→编号"的解析（只在调用者自己的店铺里找）。

**怎么防幻觉？**
三层：提示词限定只用资料；引用必须还原成真实检索到的 chunk，否则升级；再用评审模型核对"回复 vs 被引用资料"。评审是同一个模型，所以我还抽查原文。把编造从 25% 降到 5.5%，**没有降到 0**。

**一个失败的例子？**
最初的提示词里写了"资料适用的版本与客户不一致要说明"，结果约 32% 的回复出现"如果您使用的是其他版本请以实际界面为准"这类措辞，评审也多次把这类句子标为资料里没有的。是我的提示词在诱导模型往回复里加东西。

**用了多 agent 协作开发？**
是，检索层、网关内核、工单存储、沙箱、可观测、查看器、测试各由不同 agent 在各自的 git worktree 里做，我负责接口、验收、集成和真实数据上的评估。**教训**：worker 自己的单测发现不了数据层面的问题；让另一个 agent 只看接口独立写攻击性测试，发现了作者测不到的 bug。还有一次一个 agent 的最终报告被网关内容审查拦截（注入语料触发敏感词），代码和测试我另行验证后才提交。

**上过生产吗？**
没有，这是个人作品项目。

**线上延迟？**
评估时整单约 3 秒（分诊约 1.5 秒、回复约 2.5 秒）；但**一次真实走查里单次模型调用 p50 7.7 秒、最大 20 秒**，随网关负载变化很大，所以我不报一个"延迟 X 秒"的数字。没有做压力测试。

## 不要说的

- 不要说"准确率 XX%"——没有这样一个数字，只有放行率、引用命中率、评审编造率，口径各不相同。
- 不要说"解决了幻觉"或"防住了注入"。注入是 0/60，但对照也是 0/60。
- 不要说评估集是"真实工单"，不要说订单/物流是"对接了系统"。
- 不要说"实现了认证"——是请求头模拟。
- 不要把 hit@10 的 0.92 当成"检索准确率 92%"，回复节点只看前 4 个 chunk。
- 不要说"工具选择准确率 100%"——标签在看到结果后改过。
- 不要说"kill -9 验证通过"——是 Windows 的 TerminateProcess。
