# 面试讲解材料

数字都来自 README 的评估表。**讲的时候先说清楚：评估集是合成的，数字用来比较方案，不是线上效果。** 这一点主动讲，比被追问出来好得多。

## 5 分钟讲法

**1. 背景（30 秒）**
我做过售后技术支持，也做过一个客服助手：把公司知识库导进某个知识库产品，调它的 API 问答。能用，但检索是黑盒，不知道召回得好不好，没法评估，也不能执行动作。所以我做了重构：自建检索 + 工单工作流 + 评估集。

**2. 做了什么（1 分钟）**
LangGraph 的状态机：分诊 → 检索 → 带引用的回复 → 人工审核（`interrupt`，状态落 SQLite）→ 执行动作。三个我刻意做的决定：
- 引用必须在代码里校验，校验不过就升级给人，不放行；
- 笼统的先追问，需要查客户具体数据的直接升级、不让模型硬答；
- 全部路由放在一个文件里，建图和评估共用，防止评估的流程和线上分叉。

**3. 最有价值的部分：评估驱动（2 分钟）**
用知识库反向合成了 279 条评估集，然后让数字告诉我哪里错了：
- 最初放行率只有 48%。看失败原因发现两个设计错误：引用校验误杀了 38% 的可答样本（真实 chunk 编号是长路径，模型会缩写成"资料#1"甚至留空）；缺槽位就追问误拦了 20%（槽位抽取本身不可靠，准确率 0.63）。
- 修完到 81%，笼统消息的追问率从 20% 到 100%。
- 再看回复内容，发现 25% 的放行回复编造了资料里没有的具体事实，10% 把内部编号漏给了客户。原因是我自己的提示词（"版本不一致要说明""要具体"）引出来的。改提示词后降到 5.5% 和 0%，代价是放行率降了几个点，回复也短了一半。

**4. 诚实的局限（1 分钟）**
评估集是合成的，偏乐观；评审和被评是同一个模型；剩下 5.5% 的编造没解决；Docker 没验证过；工单系统是 mock。混合检索和重排没有带来端到端的提升，所以默认用 BM25。

**5. 如果有真实数据（30 秒）**
最想做的是拿真实历史工单替换合成评估集，再看这些数字还成不成立。

## 预期追问和实话

**为什么不用 Dify / Coze？**
这个场景的价值在于：能做评估、能定制路由逻辑、能控制引用校验。拖拽平台做简单问答很快，但我要的是"能量化每次改动的效果"，代码里更容易做。（不要贬低别人的工具，说取舍。）

**为什么只用 LangGraph + LangChain 的一部分？**
LangChain 只用了模型接入和结构化输出，编排用 LangGraph，因为工单有分支、有状态、要人工介入，`interrupt` + checkpoint 正好对应。没有用 agent 的自由工具调用：这个场景的流程是确定的，让模型自由决定下一步只会增加不确定性。

**为什么不做 multi-agent？**
流程确定，一个图加几个节点就够；多 agent 在这里只会增加成本和排查难度。

**混合检索为什么没用？**
我做了，也调了权重（dev/test 拆分）。检索层面在 test 半边略好但不显著，端到端没有更好，还要多装一个模型、预建 20 分钟的索引。客户习惯贴报错原文和平台名，BM25 本来就强。数据没有支持"必须用向量"，所以默认 BM25，配置里可以切换。

**评估集怎么来的？可信吗？**
用知识库文档反向让模型写客户消息，文档就是标准答案；有防照抄校验（和原文连续相同 ≥12 字就拒收）；类别标签按文档目录机械打，不交给模型。**不完全可信**：用词偏近原文、一个样本只标一个答案文档。所以我把它当"比较方案的尺子"，不当线上指标。

**怎么防幻觉？**
三层：提示词限定只用资料；引用必须还原成真实检索到的 chunk，否则升级；再用评审模型核对"回复 vs 被引用资料"。评审是同一个模型，所以我还抽查原文。这套机制把编造从 25% 降到 5.5%，**没有降到 0**。

**一个失败的例子？**
我最初的提示词里写了"资料适用的版本与客户不一致要说明"，结果约 32% 的回复（正则统计 60/188）出现了"如果您使用的是其他版本请以实际界面为准"这类措辞，评审也多次把这类句子标为资料里没有的。是我的提示词在诱导模型往回复里加东西。

**用了多 agent 协作开发？**
是，检索层、清洗、评估脚本、测试各由不同 agent 实现，我负责接口、验收和真实数据上的评估。最大的教训是：worker 自己的单测发现不了数据层面的问题，指标分母算错（不可答样本把所有命中率压低 15%）、知识库里 11.5% 的字符是表格二进制乱码，都是在真实数据上才发现的。

**上过生产吗？**
没有，这是个人作品项目。

**线上延迟和成本？**
分诊约 1.5 秒、回复约 2.5 秒，单条工单总计约 3.5 秒（网关繁忙时我测到过 19 秒，分诊节点本身就慢了 7 倍）；每条工单 2 次模型调用，需查数据的和笼统的更少。我没有做压力测试。

## 不要说的

- 不要说"准确率 XX%"——没有这样一个数字，只有放行率、引用命中率和评审给的编造率，口径各不相同。
- 不要说"解决了幻觉"。
- 不要说评估集是"真实工单"。
- 不要把 hit@10 的 0.92 当成"检索准确率 92%"，回复节点只看前 4 个 chunk，对应的是 chunk_hit@4。
