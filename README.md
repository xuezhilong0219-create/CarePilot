# CarePilot：售后工单助手

面向电商 ERP（旺店通）售后技术支持场景的工单助手。收到客户消息后：分诊 → 检索知识库 → 生成**带可校验引用**的回复 → 人工审核 → 执行动作；回答不了的升级给对应团队，说得太笼统的先追问。

这是一个个人作品项目，**不是生产系统**：知识库是我做售后技术支持时用过的内部 wiki 导出，工单系统是 mock，评估集是 LLM 反向合成的。数字用来比较方案，不代表线上效果（见「局限」）。

技术栈：LangChain（模型与结构化输出）+ LangGraph（状态机、`interrupt` 人工审核、SQLite checkpoint）+ FastAPI（同步与 SSE 流式）。

## 它解决什么问题

最初我用某知识库产品的 API 做过一个客服问答，检索是黑盒：不知道 chunk 怎么切、召回得好不好，也没法评估和调参，更不能执行动作（升级、回复）。CarePilot 是重构：自建检索，把"能不能自动回答"拆成可测试的决策，并用评估集量化每次改动的效果。

## 工作流

```
工单 → classify（类别/严重度/实体/是否笼统）
        ├─ 笼统 ───────────────→ 追问
        ├─ 需查客户具体数据 ────→ 升级（不检索、不生成）
        └─ 其余 → 检索 → 生成回复（带引用）
                          ├─ 能答且引用有效 → 人工审核（interrupt）→ 发送
                          ├─ 答不了且缺信息 ─→ 追问
                          └─ 答不了 ─────────→ 路由到团队 → 人工审核 → 升级
```

流程图和设计取舍见 [docs/architecture.md](docs/architecture.md)。

## 快速开始

```bash
uv sync
cp .env.example .env          # 填 LLM_API_KEY / LLM_BASE_URL（OpenAI 兼容网关）
uv run pytest -q              # 不需要网络和 key，用假模型
uv run uvicorn carepilot.api.app:app --port 8000
```

默认用仓库自带的**示例知识库**（`data/kb/`，合成数据，仅供演示和测试）。用真实知识库：

```bash
uv run python scripts/build_kb.py --raw <导出目录> --out data/kb_real   # 清洗，不调用 LLM，几秒
KB_DIR=data/kb_real uv run uvicorn carepilot.api.app:app --port 8000
```

```bash
# 创建工单（同步）。status 为 awaiting_review 时需要人工审核
curl -X POST localhost:8000/tickets -H 'content-type: application/json' \
  -d '{"message":"库存同步失败，提示“商品服务调用失败”，怎么处理？"}'
# 审核：approve / edit（带 reply）/ reject
curl -X POST localhost:8000/tickets/<thread_id>/review -H 'content-type: application/json' \
  -d '{"action":"approve"}'
# 流式：每个节点完成发一个 SSE 事件，最后一个 result 事件内容与同步响应一致
curl -N -X POST 'localhost:8000/tickets?stream=true' -H 'content-type: application/json' -d '{"message":"..."}'
```

## 评估结果

评估集 279 条（可答 203：功能 146 / 平台对接 25 / 规则变更 19 / 仓库物流 13，其中 45 条带报错原文；需查数据 24；无关 12；笼统消息 40）。全部用 `deepseek-v4.1-flash-1017`，检索 BM25。

### 端到端：每次改动前后

| 版本 | 可答：放行且引用命中 | 需查数据→升级 | 笼统→追问 |
|---|---|---|---|
| 最初版本 | 98/203 = 48% | 23/24 | 8/40 = 20% |
| 修复引用校验 + 两层追问 | 164/203 = 81% | 22/24 | 40/40 |
| 再加：需查数据直接升级 | 169/203 = 83% | 24/24 | 39/40 |
| 再改：回复提示词禁止编造 | 159/203 = 78% | 24/24 | 39/40 |

最后一行看似倒退，是用一部分放行率换回复质量（见下表）。**"放行且引用命中"在不同次运行之间会有几条的波动**：第二行和第三行对可答样本走的几乎是同一条路径（仅分诊提示词里 `data_exception` 的定义不同，且那一版已没有可答样本被判成该类），却差了 5 条。我没有对同一份代码做过重复运行，所以只能说波动大约是这个量级，相邻两行相差几条不能当作结论。

### 回复质量（评审模型逐条核对"回复 vs 被引用资料原文"）

| | 具体事实无依据 | 仅无害多余内容 | 无编造 | 回复含内部资料编号 | 平均长度 |
|---|---|---|---|---|---|
| 修订提示词前（188 条） | 25.5% | 47.3% | 27.1% | 10.6% | 335 字 |
| 修订提示词后（183 条） | 5.5% | 3.8% | 90.7% | 0% | 138 字 |

**这是同一个模型评自己，存在自我偏好，数字偏乐观。**评审给出的"无依据"我抽查了 3 条对照原文，3 条都属实（编造了原文没有的操作步骤、把版本号安在了错误的功能上、说了原文没有的一列）。5.5% 说明剩余问题仍存在，没有解决。

### 检索（203 条可答，客户原话直接检索）

| 检索器 | hit@1 | hit@10 | chunk_hit@4 | 单次耗时 |
|---|---|---|---|---|
| BM25（默认） | 0.645 | 0.916 | 0.808 | <1 ms |
| 纯向量 bge-small-zh | 0.389 | 0.709 | 0.601 | 5 ms |
| 混合，等权重 | 0.552 | 0.916 | 0.837 | 6 ms |
| 混合，向量权重 0.25 | 0.621 | 0.926 | 0.857* | 10 ms |
| 混合 + bge-reranker-base | 0.606 | 0.931 | 0.867 | 5.4 s |

`chunk_hit@4`：回复节点实际只看到前 4 个 chunk，里面有标准答案的比例，最贴近线上。
\* 向量权重在 dev 半边（111 条）上调，在 test 半边（92 条）上 chunk_hit@4 为 0.848，BM25 为 0.804，**提升不显著**。端到端上混合检索没有更好（解决率 78% 对 83%，在噪声边缘），所以默认用 BM25：客户习惯贴报错原文、平台名、功能名，这种精确匹配 BM25 本来就强（带报错原文的样本 hit@10 达 0.98）。

## 局限（面试前要先讲清楚）

- **评估集是 LLM 用文档反向合成的**，问题用词天然偏近原文，BM25 的数字偏乐观。我抽查过一部分，没有逐条人工审核。真实工单上的表现需要真实数据验证。
- **每个样本只标了一个标准答案文档。**另一篇文档也能答对时，检索到它会被算作没命中。我同时报严格和宽松两档，只能缓解。
- **类别标签是按文档所在目录机械打的**，不一定等于客户的真实意图，所以分诊准确率（约 64%）我不用来调提示词。
- 评审和被评的是同一个模型。
- `笼统消息` 的 40 条是我手写的，前 20 条和分诊提示词里的示例有重合，后 20 条是之后新写的、未出现在提示词里，两批结果都是 19/20 和 20/20 追问。
- **未验证**：Docker 镜像没有构建过（本机没有 docker），只做了配置文件的语法检查；没有做并发和压力测试；mock 的工单系统没有对接真实系统。
- 向量索引离线构建约 20 分钟（2.2 万个 chunk，CPU），本项目没有做增量更新。

## 项目结构

```
src/carepilot/
  graph/        状态、节点、路由（routing.py 建图与评估共用）、建图
  retrieval/    BM25（倒排）、向量、RRF 混合、重排、factory
  ingest/       知识库清洗（纯规则，确定性）
  evaluation/   指标、运行器、评估集生成
  api/          FastAPI
eval/           评估与实验脚本（真实评估集和报告在 eval/real，不入库）
scripts/        build_kb.py、build_index.py
docs/           架构说明
tests/          184 个测试，均不依赖网络和真实数据
```

## 配置

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `LLM_API_KEY` / `LLM_BASE_URL` | 必填 | OpenAI 兼容网关 |
| `LLM_FAST_MODEL` / `LLM_MAIN_MODEL` | `deepseek-v4.1-flash-1017` | 分诊 / 回复 |
| `RETRIEVER_KIND` | `bm25` | `vector` / `hybrid` / `hybrid_rerank_ce` / `hybrid_rerank_llm` |
| `KB_DIR` | `data/kb`（示例） | 知识库目录 |
| `INDEX_DIR` | `data/index/<KB 目录名>` | 向量索引目录 |

## 开发过程

这个项目用多个 AI 编程 agent 协作完成（检索层、知识库清洗、评估脚本、测试与 API 分别由不同 agent 实现，我负责接口设计、验收和真实数据上的评估）。`.team/` 保留了当时的协作规则和任务说明。worker 自己的单测发现不了的问题（指标分母、引用被长编号误杀、槽位硬门槛、知识库乱码）都是在真实数据上跑评估才暴露的。
