# CarePilot：售后工单助手

[![check](https://github.com/xuezhilong0219-create/CarePilot/actions/workflows/ci.yml/badge.svg)](https://github.com/xuezhilong0219-create/CarePilot/actions/workflows/ci.yml)

面向电商 ERP 售后技术支持场景的**工单 Agent**。不只是检索问答：它会查订单/物流/店铺授权/工单进度，对外发送和改状态必须经人工批准，所有动作过一个**没有模型参与判定的工具网关**（四道闸、审计、幂等、崩溃恢复、预算守卫），每次运行落一份节点级 trace，并有评估集度量每次改动的效果。

这是一个个人作品项目，**不是生产系统**：知识库是我做售后技术支持时用过的内部 wiki 导出；订单/物流/店铺是**合成的沙箱数据**；角色靠请求头模拟，**没有真正的认证**；评估集是 LLM 反向合成的。数字用来比较方案，不代表线上效果（见「局限」）。逐项对照功能清单的验收状态见 [docs/status.md](docs/status.md)。

技术栈：LangChain（模型与结构化输出）+ LangGraph（状态机、`interrupt` 人工审核、SQLite checkpoint）+ FastAPI（同步与 SSE 流式）+ SQLite（工单存储、网关账本与审计）。

## 它解决什么问题

最初我用某知识库产品的 API 做过一个客服问答，检索是黑盒，也不能执行动作。检索问答现在很常见，所以 CarePilot 把重心放在**让 Agent 敢动手**所需要的东西上：

- **模型只能提议，不能决定。**规划模型只看客户说过的话，只能提议只读查询；订单号必须逐字出现在客户消息里才会执行；写操作和对外发送只由确定性代码在人工批准后经网关执行。
- **越权和"不存在"不可区分。**查别家店铺的订单与查一个不存在的订单，回复逐字相同。
- **可以崩、可以重放。**幂等键、账本、对账：进程被强杀后恢复，副作用恰好一次。
- **能解释、能回溯。**每个动作进审计（含被拒绝的），每次运行一份节点级 trace，成本 = 实测 token × 你配置的单价。

## 工作流

```
工单 → classify（类别/严重度/实体/是否笼统，带上对话历史和之前累积的槽位）
        ├─ 笼统 ─────────────────→ 追问（通用："具体是什么问题"）
        ├─ 需查客户自己的数据 ───→ plan_tools：规划→只读工具（最多 4 步，守卫防死循环）
        │                           ├─ 查到 → 依据查询结果生成回复
        │                           ├─ 没查到/无权（回复逐字相同）/参数不对 → 追问
        │                           ├─ 物流接口超时 → 固定降级文案，不经模型
        │                           └─ 没有合适工具 → 升级
        └─ 其余 → 检索（客户说了版本就按产品线过滤）→ 生成回复（带结构化引用）
                          ├─ 能答且引用有效 → 草稿存为工单内部备注 → 人工审核
                          ├─ 答不了且缺信息 ─→ 追问
                          └─ 答不了 ─────────→ 路由到团队 → 人工审核 → 升级
人工审核 approve →（网关：批准）→ 客户看不到任何回复 →（二次确认）→ 发送，幂等；重复确认不产生第二条消息
升级 → 网关执行 escalate_ticket，写入原因和已完成动作 → /handoff 给下一个坐席
任意节点超预算/循环 → 只留内部备注并标 needs_human，不替人改状态
```

流程图和设计取舍见 [docs/architecture.md](docs/architecture.md)。

## 上下文预算（对话历史不是全塞进去）

长工单会越聊越长，而提示词是有代价的。所以历史先过一道预算（`src/carepilot/graph/context.py`）：

- **放得下就一个字都不动**——短会话不该为压缩付代价；
- 放不下时：最近 3 轮逐字（每轮 600 字，比原来放宽一倍，因为贴报错的工单错误码常在后半段），更早的每轮压成一行摘要（只取第一句），还装不下就从最旧的开始丢；
- 压的是**措辞**，不是**事实**：摘要只做句子切分和截断，不生成新句子，单测钉死了「每行正文都必须是某条原文的前缀」；
- 回复节点以前完全看不到历史（客户说「这个」只能硬猜），现在也带上压缩后的历史。那一条「历史只能用来理解指代」的说明是**条件注入**的：只有真的带了历史才追加。第一版是常驻的，结果单轮对话的提示词也被改了一个字节，评估基线当场掉了 4 条（见下面的局限）——所以单轮的提示词现在和改动前完全一致，单测直接比对 `DRAFT_PROMPT` 是否相等。

```bash
uv run python eval/measure_context.py   # 改动前后各塞多少 token，不需要模型和密钥
```

实测（`--budget 3000`，`uv run python eval/measure_context.py`）：

| 会话 | 轮数 | 旧实现（6 轮 × 300 字） | 新实现 |
| --- | --- | --- | --- |
| 3 轮短会话 | 4 | 992 token，逐字 4 轮 | 992 token，逐字 4 轮（未压缩） |
| 10 轮普通会话 | 10 | 1781 token，**只覆盖 6 轮，丢 40% 正文** | 2969 token，覆盖 10 轮，丢 0% |
| 30 轮长会话 | 30 | 1781 token，**只覆盖 6 轮** | 1843 token，覆盖 30 轮 |
| 100 轮马拉松 | 100 | 1781 token，**只覆盖 6 轮** | 2987 token，覆盖 54 轮（有上界，不随轮数线性增长） |

上面那张表只证明「塞进去多少」。真正要回答的是「多轮答得更对吗」，而评估集是单轮的，端到端指标对这个问题是盲的。所以另写了一个两轮脚本 `eval/run_multiturn.py`：

- 第一轮用评估集里的可答**原话**，第二轮只给一句指代（「具体要在哪儿改」「这个设置叫什么名字」「步骤能再说一遍吗」）——单看这句话，人也不知道在说什么；
- 两臂跑同一批会话，**唯一差别是第二轮带不带历史**；第一轮只跑一次（没有历史，两臂完全一样），所以调用量是 12 × 3 轮；
- 判分不调模型：第二轮检索到的文档是否还是评估集里那篇 gold（宽严两档）、回复有没有可校验引用、有没有重新索要第一轮已经给过的信息。

```bash
uv run python eval/run_multiturn.py --kb-dir data/kb_real
```

| 臂 | 第二轮命中同一篇文档 | 有可校验引用 | 自动回复 |
| --- | --- | --- | --- |
| 带历史 | **11/12 = 0.917** | 9/12 | 9/12 |
| 不带历史 | **0/12** | 0/12 | 0/12 |

不带历史时 12 条全部落进「请描述一下具体遇到的问题」——这不是 bug，是设计：一句只有指代的话，系统确实没有依据。带历史时仍有 3 条升级、1 条检索偏到了别的文档，说明压缩过的历史不是万能的。这个脚本的局限也要说清楚：只有 12 段会话、第二轮句式固定三种、gold 标签来自单轮数据集，所以它证明的是「历史让指代落回原文档」，不是「多轮对话的整体质量」。

不过它反过来暴露了一件事，值得记下来：第一版把那条说明常驻在提示词里，等于把单轮对话的提示词也改了，`eval_all --quick` 的答对率从 0.872 掉到 0.769、误拒从 0.051 升到 0.128；改成条件注入后连跑两次是 0.846 / 0.077 和 0.846 / 0.026（n=39，同一个分层抽样）。也就是说，**给一个用不到历史的场景加一句关于历史的规则，确实会把回答推向拒答**（3~4 条）。条件注入后剩下的 1 条差距不能声称是零代价：同一个配置重复两次，误拒就在 1 条和 3 条之间跳，这说明 ±1~2 条属于噪声量级。

## MCP 通道（让别的 agent 用这些工具）

九个工具按 [Model Context Protocol](https://modelcontextprotocol.io) 暴露，任何支持 MCP 的客户端（Claude Desktop、自己的 agent 循环）都能直接接，不用为它写 HTTP 包装。

```bash
# stdio：客户端负责进程生命周期，--user 决定身份，--run-id 决定幂等键的 run 部分
# 这条通道不调用模型，所以不需要 LLM_API_KEY——只想拿工具用的客户端不必填一个假密钥
uv run python -m carepilot.mcpserver --user a1 --run-id demo-run
```

**为什么中间还隔着网关。** MCP 规范里没有权限模型——没有角色、没有审批流、没有审计表。服务器只能决定「暴露哪些工具」，决定不了「这一次调用能不能做」，谁连上谁就能调。所以这里刻意只做传输层：MCP 负责把 schema 和结果搬到对面，`gateway.call()` 仍然决定能不能执行。结果是三种，都是正常返回而不是异常：

| outcome | 什么时候 | 含义 |
|---|---|---|
| `executed` | 只读工具、内部写 | 已执行，带 `replayed` 说明是命中幂等账本回放还是真的跑了一次 |
| `needs_approval` | 改状态、对外发送、升级 | **只登记提议，不执行**。审批需要人，而这条通道上没有人 |
| `rejected` | 参数不合规、无权限、状态机不允许 | 带 `gate` 和 `code`（如 `role_denied`、`illegal_transition`） |

几个刻意的点：

- **schema 是推出来的，不是抄的。** `inputSchema` 由 `ToolSpec.args_model` 的函数签名生成（`src/carepilot/mcpserver.py` 的 `tool_signature`），所以 pydantic 里的 `pattern`、`maxLength` 原样进了 JSON Schema——模型知道 `order_id` 要匹配 `^[A-Za-z0-9-]{6,32}$`，不用靠猜。约束仍然由网关再校验一遍，MCP 那层只是帮模型少犯错。
- **身份来自启动参数，不来自客户端。** MCP 客户端不携带用户身份，所以 `--user` 按用户表还原角色和店铺范围，和 HTTP 接口一样不信任调用方自报的角色。没有认证的 MCP 服务器 = 谁连上谁就能调，这是 MCP 本身的性质，不是这里偷懒。
- **一次进程 = 一个 run。** 同一进程内重复的等价调用命中幂等账本回放，不产生第二次副作用。
- **权限和店铺范围照常生效。** 客户身份调写工具拿到 `role_denied`；查别人店铺的订单，和查一个不存在的订单返回完全相同的 `{"found": false}`。

验证在 `tests/test_mcp_server.py`（12 条）：工具清单与注册表一一对应、schema 带着 pattern、只读调用写审计、重复调用回放、写操作只拿到 `needs_approval` 且工单状态没变、权限与范围过滤、未知用户拒绝启动、**不配 LLM 密钥也能启起来**，外加一条**真子进程走 stdio** 的端到端（其余测试直接调 `server.call_tool`，绕过了传输层）。

## 快速开始

```bash
uv sync
cp .env.example .env          # 填 LLM_API_KEY / LLM_BASE_URL（OpenAI 兼容网关）
uv run pytest -q              # 不需要网络和 key，用假模型
uv run python scripts/check.py  # 门禁：ruff + pytest（CI 跑的就是这条）
uv run uvicorn carepilot.api.app:app --port 8000
```

默认用仓库自带的**示例知识库**（`data/kb/`，合成数据，仅供演示和测试）。用真实知识库：

```bash
uv run python scripts/build_kb.py --raw <导出目录> --out data/kb_real   # 清洗，不调用 LLM，几秒
KB_DIR=data/kb_real uv run uvicorn carepilot.api.app:app --port 8000
```

服务默认是**治理模式**，所有接口需要 `X-User-Id` 头。演示用户（角色和店铺范围取自用户表，请求自报的角色无效）：客户 `c1`（店铺 S1、S2）、`c2`（S3）、`c3`（S4），坐席 `a1`、`a2`，管理员 `admin1`。

> **Windows 终端注意**：在 Git Bash / cmd 里用 `curl -d '含中文的 JSON'` 内联传中文时，请求体可能被终端按 GBK 编码，服务端会返回 `400 There was an error parsing the body`（服务端只接受 UTF-8，我用 GBK 编码的请求体复现过）。要么把 JSON 放进 UTF-8 文件用 `--data-binary @msg.json`，要么直接用 Python 的 `httpx`/`requests`。下面的示例在 Linux/macOS 终端可以直接用。

```bash
# 客户开单（示例知识库里答得出的问题）。status=awaiting_review 表示有草稿等坐席审核；need_info 表示系统在追问
curl -X POST localhost:8000/tickets -H 'X-User-Id: c1' -H 'content-type: application/json' \
  -d '{"message":"店铺授权过期了怎么办"}'
# 客户在同一张工单里继续说（历史和已识别的平台/店铺/功能会带进下一轮）
curl -X POST localhost:8000/tickets/T-000001/messages -H 'X-User-Id: c1' -H 'content-type: application/json' -d '{"message":"还是不行"}'
# 坐席审核：approve / edit（带 reply）/ reject。回复类工单默认两步：批准后客户仍收不到回复
curl -X POST localhost:8000/tickets/T-000001/review -H 'X-User-Id: a1' -H 'content-type: application/json' -d '{"action":"approve"}'
# 二次确认才真正发送（幂等：重复确认只发一条，工单置为 resolved）
curl -X POST localhost:8000/tickets/T-000001/confirm -H 'X-User-Id: a1'
# 交接摘要 / 审计 / 引用原文（只给坐席和管理员）
curl localhost:8000/tickets/T-000001/handoff -H 'X-User-Id: a2'
curl localhost:8000/tickets/T-000001/audit -H 'X-User-Id: a1'
# 流式：每个节点完成发一个 SSE 事件，最后一个 result 事件内容与同步响应一致
curl -N -X POST 'localhost:8000/tickets?stream=true' -H 'X-User-Id: c1' -H 'content-type: application/json' -d '{"message":"..."}'
```

审核卡有两种：**回复草稿**（`resolution=auto_reply`）的 `approve` 走"批准 → 二次确认 → 发送"；**升级卡**（`resolution=escalate`，知识库答不了或要查账单）的 `approve` 就是"确认升级"，直接执行 `escalate_ticket`，没有待确认的发送——这时再调 `/confirm` 返回 409 是正常的。后续轮次里系统判断资料不足也会把原来的回复草稿变成升级。

旧的"演示模式"（无身份、mock 工单系统）仍保留：`create_app(governed=False)`。

每次运行落一份 trace JSON 到 `data/traces/`，用 `uv run python scripts/trace_viewer.py --traces data/traces --out viewer.html` 生成可按节点展开的单文件查看器；成本报表见 `scripts/cost_report.py`（单价需要你自己填 `pricing.json`，不会替你编价格）。一键评测：`python eval/eval_all.py --quick`（本机没有 `make`；Makefile 只是转发）。

## 界面（用浏览器点，不用 curl）

```bash
uv run uvicorn carepilot.api.app:app --port 8000
# 打开 http://127.0.0.1:8000/
```

右上角切身份（`c1`/`c2`/`c3`/`a1`/`a2`/`admin1`，就是换 `X-User-Id`）。三栏：左边工单列表，中间会话，右边坐席的处理台。一条完整链路在浏览器里是这样的：

1. 客户点「＋ 新建」，写下问题；提交后中间栏逐个亮起节点（分诊 → 检索 → 起草 → 待审核），亮的是真的 SSE 事件，不是假进度条。
2. 切到 `a1`，右侧出现**待审核**：草稿全文、引用卡片（点开看知识库原文）、审核备注输入框。
3. 点「通过并发送」→ 工单变成**待二次确认**，右侧出现确认卡片；再点「确认发送（真实动作）」→ 消息进会话、工单置 `resolved`。
4. 「交接摘要」「审计流水」懒加载后端的 `/handoff` 与 `/audit`，审计里能看到 `needs_approval → approved → confirmed → executed` 这一串。

升级卡（知识库答不了、要查账单）在界面上是「建议升级 + 升级原因」，按钮变成「确认升级」，没有二次确认的发送——因为根本没有对外发送这一步。

几个刻意的取舍：

- **单文件、无框架、无构建链**：`src/carepilot/api/ui.py` 一个 Python 字符串装下 HTML/CSS/JS，`GET /` 直接吐出来。没有 npm、没有打包产物、不做 SSR——这是个演示台，不是产品前端。
- **页面不内嵌任何业务数据**：`render_ui()` 只替换 CSP 和演示用户两个常量，工单内容全部由浏览器 `fetch` 拿 JSON 再用 `createElement`/`textContent` 建 DOM。`tests/test_ui.py` 里有一条用 `<img onerror>` 当工单标题，断言首页 HTML 里搜不到它。
- **CSP 收得很紧**：`default-src 'none'; connect-src 'self'; style-src 'unsafe-inline'; script-src 'unsafe-inline'; img-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`。没有外链字体、图标、CDN。
- **身份只是下拉框**：切换身份就是换一个请求头，背后没有登录。这跟前端无关——后端的认证本来就是假的，README 局限里写了。

已知没做的：SSE 断了不自动重连（刷新页面即可）；进度条在结果回来后清空，不保留历史节点；审计固定取 500 行，前端只显示最后 40 条。

## 质量门禁

```bash
uv run python scripts/check.py              # ruff + 全量测试（CI 跑的就是这一条）
uv run python scripts/check.py --skip tests # 只跑 lint，改完一处马上看
```

- **为什么是一条脚本，不是 Makefile**：`make` 在 Windows 上默认没有；脚本用 `sys.executable`，三平台一致。`Makefile` 里的 `check` 只是转发到它。
- **为什么仓库里没有 CI 配置文件**：这个仓库没有 remote（`git remote -v` 为空）。放一个永远不会跑的 workflow 只是装饰。接上 remote 后，job 里就一行 `uv run python scripts/check.py`。
- **lint 规则只挑会和 bug 有关的**：`E4`（未使用导入）、`E7`、`E9`（语法/运行时错误）、`F`（pyflakes）、`B`（bugbear）。忽略 `B008`（FastAPI 把 `Depends(...)` 写在默认值是固有写法）和 `E731`（`eval/` 里用 lambda 做聚合更直接）。
- **不跑 `ruff format`**：它会把全仓重排一遍，之后每个 diff 都失去信息。格式化是另一件事，没有和"找 bug"绑在一起。
- 规则开起来当场就找到三个真问题，都不是格式问题：注入评测的**伪造引用检查永远不触发**（调用点把模型写的裸编号拼成了 `doc#N`，跟载荷里的假文档号永远不等，等于那条检查没跑过）；18 处线程/闭包目标捕获循环变量（当前迭代安全，改一次循环就漂）；6 处 `zip()` 没有 `strict=`（长度不一致会静默截断）。这些用"读代码"没看出来，`ruff check .` 一开就点名了。

## 评估结果

### 交叉评审（同一批回复，换一个家族的模型再评一遍）

单模型自评是这套评估最容易被质疑的一点，所以我把同一个评分标准（提示词、`Verdict` 结构逐字相同，`eval/judge_cross.py` 直接 import 过来用）交给第二个家族再跑一遍：

| | 评审 A：deepseek-v4.1-flash-1017（同族） | 评审 B：qwen3.8-max（异族） |
|---|---|---|
| 无编造 none | 87.2% | 72.3% |
| 仅无害多余 minor | 6.9% | 16.0% |
| 具体事实 major | 5.9% | 11.7% |
| 答了所问 answers | 98.9% | 98.9% |

188 条自动放行回复，两个评审都成功。逐条一致率：level **0.840**（Cohen's kappa **0.545**），answers 1.000（kappa 1.000）。不一致的 30 条全部是"A 判 none、B 判 minor/major"（19 + 9 条），没有反向的。

怎么读：

- **同族评审确实偏乐观。**换家族之后"具体事实无依据"从 5.9% 变成 11.7%，大约翻倍。所以上面那个 90.7% 的"无编造"要读成"同一家族的模型认为没问题"，不是事实。
- **answers 这一维是稳的**（98.9% 对 98.9%，kappa 1.000）——它几乎全判 true，稳定但信息量低，不能拿来当"回复都对"的证据。
- **level 的 kappa 只有 0.545（中等一致）**：14% 的样本两个模型给出不同等级。聚合比例还能用，**逐条结论不能引用**。
- 这一轮还揪出一个真 bug：两个模型在判了 `major` 之后，把级别词本身写进"摘句"字段，修提示词前分别是 21/23 和 41/41 —— 等于 `--show-fail` 打出来给人看的是废话，而它只能靠换一个模型看明细时发现。收紧提示词后 0/24、0/52。

不证明的事：**一致不等于正确**。两个模型可能一起错，rubric 偏松的问题没有被这次测量修掉；这里量的是"结论是不是某一个模型的口味"，不是"回复对不对"。

### 并发：锁只夹记账，不夹执行

网关原来把操作系统文件锁一路握到工具执行结束，等于所有工具调用（包括只读查询）在同一个库上串行。改法是让锁只覆盖账本事务——预留一行 `started`、记账、审批状态、对账；工具在锁外执行。「恰好一次」由那行 `started` 保证，不是靠锁一直握着。

`uv run python eval/bench_gateway.py --procs 8`（假工具、纯本地、不调用模型）：

| 场景 | 并发 | 工具耗时 | 墙钟 | 单次 p50 | 并行度 |
|---|---|---|---|---|---|
| 改动前（锁跨过执行） | 16 | 100 ms | 1.88 s | 990 ms | 0.85× |
| 改动后（锁只夹记账） | 16 | 100 ms | 0.25 s | 184 ms | **6.50×** |

- 同一 run、同一参数打 16 次：`executed` 1 次、`replayed` 15 次，副作用文件里只有 1 行。
- 跨进程 8 个各查一单：墙钟 0.23 s（串行下界 0.80 s），并行度 3.49×，副作用 8 行。
- **仍然串行的部分**：审批后执行的 `STATE_CHANGE` / `EXTERNAL_SEND` 故意留在锁内（低频、人工触发，审批状态机语义一行没改）；SQLite 的所有写入本身也按库串行。所以这不是「做完了并发」，只是「把不必要的那一段挪出去了，并且量过」。

### 卡住的调用：对账入口，以及它凭什么知道谁在跑

工具挪到锁外之后，「这条调用还在执行」不能再用锁判断了——所以执行期间会在 `<db>.leases/<idem_key>` 上加一把**文件锁**，这就是在飞租约。对账探到锁在就跳过（`skipped_inflight`），锁没了说明上一个执行者不在了，可以接管。

不用 pid 判活是有原因的：Windows 上 `os.kill(pid, 0)` 不是探测而是 `TerminateProcess`，`OpenProcess` 在进程刚被强杀后仍可能返回句柄（实测踩到），pid 还会复用。文件锁由操作系统在进程消失时释放，正好等于「锁在 = 真在跑」。

```bash
# 先看：不调 verify、不写库、不写审计
curl -X POST -H "X-User-Id: admin1" "localhost:8000/admin/reconcile?dry_run=true"
# 再看有没有卡住的调用，以及它有没有活租约
curl -H "X-User-Id: admin1" localhost:8000/admin/inflight
# 真对账（仅管理员）
curl -X POST -H "X-User-Id: admin1" "localhost:8000/admin/reconcile?min_age_s=300"
```

定时扫描默认**关闭**（`RECONCILE_INTERVAL_S=0`）：对账可能认领一条副作用并记成 `done`，是写库动作，开不开该由部署环境决定；`docker compose` 里默认打开（间隔 60 s、只处理 300 s 以前的）。两个入口都是管理员专属，13 条测试钉住「在飞的不碰、太新的不碰、dry run 什么都不写」。


### 延迟：时间花在模型上，不在网关

`uv run python eval/latency_profile.py --limit 40`（可答样本里等距抽 40 条，串行跑，BM25，2026-11-17）：

| 节点 | 样本 | p50 | p95 | 均值 | 最大 |
|---|---|---|---|---|---|
| 分诊 classify | 40 | 2.98 s | 4.45 s | 2.93 s | 5.72 s |
| 检索 retrieve | 40 | 1 ms | 2 ms | 1 ms | 4 ms |
| 起草 draft_reply | 40 | 3.01 s | 6.14 s | 3.19 s | 8.25 s |
| 整单 total | 40 | 6.01 s | 8.95 s | 6.12 s | 10.42 s |
| 模型调用合计 | 40 | 6.01 s | 8.95 s | 6.12 s | 10.42 s |
| 本地计算（检索/渲染/记账） | 40 | 1 ms | 2 ms | 1 ms | 4 ms |

- **两次模型调用就是整单**：分诊 2.98 s + 起草 3.01 s ≈ 整单 6.01 s，本地那点工作被四舍五入掉了（p50 1 ms）。
- **检索不是瓶颈**：BM25 全库打分 p50 1 ms、p95 2 ms。这也是没有上向量库的理由之一——换掉它省不下时间，只会多出延迟。
- **网关不在这条路径上**：这 40 条都是单轮可答样本，一次工具都没调。网关自身的成本在 `bench_gateway.py` 里单独量过：16 次调用 0.25 s，扣掉假工具那 100 ms，每次约 16 ms（含线程调度）。
- **口径**：串行跑（`--concurrency 1`）。并发会让请求在模型侧排队，测出来的就不是「一次要多久」而是「排队多久」。只在这台机器、当天、这个网关上量过；换个模型或网关繁忙时段，绝对值会变，比例不会。
- 明细留在 `eval/real/reports/latency/*.items.jsonl`，`--from-items` 可以拿它换统计口径重算，不用再调一次模型。

### 流式：量过了，先不改

起草这一步 p50 3.01 s 里客户什么都看不到，直觉是流式输出。`uv run python eval/ttft_probe.py --limit 6` 量了同一条 prompt（和线上共用 `nodes.draft_messages`，不是另抄一份）：

| 量的是哪一段 | 样本 | p50 | p95 | 最大 |
|---|---|---|---|---|
| 首字（第一个非空 chunk） | 6 | 1.27 s | 3.64 s | 4.13 s |
| 整段（流结束） | 6 | 1.67 s | 4.05 s | 4.60 s |

结论是**先不改**：

- **结构化输出给不了增量。**`with_structured_output(DraftResult).stream()` 只吐一个 chunk，要等整个 JSON 解析完才给对象（实测单次 6 秒后一次性到）。所以流式的前提是把起草改成自由文本、再用代码解析 `[n]` 做引用校验。而自由文本实测 **0/6** 条带 `[n]`（另有 2/6 把 `cited_ids: ["1","2"]` 当正文末尾写出来），引用校验会全灭——这是拿 0.803 的可答率基线去换 1.7 秒白屏：首字最早也只能在分诊 2.98 s + 起草首字 1.27 s ≈ 4.3 s 出现，分诊那一段省不掉。
- **自由文本确实更快**（整段 p50 1.67 s 对结构化 3.01 s），但这里限了 `--max-tokens 512`、结构化那条没限，差距里有长度差，不能全算成格式开销。真要省时间，先验「模型肯不肯在正文里写 `[n]`」比先改契约划算。
- 6 条单次采样，不是 SLA。脚本退出码与延迟账一致：没有样本退出 2，正常 0。

## 局限（面试前要先讲清楚）

- **评估集是 LLM 用文档反向合成的**，问题用词天然偏近原文，BM25 的数字偏乐观。我抽查过一部分，没有逐条人工审核。真实工单上的表现需要真实数据验证。
- **每个样本只标了一个标准答案文档。**另一篇文档也能答对时，检索到它会被算作没命中。我同时报严格和宽松两档，只能缓解。
- **类别标签是按文档所在目录机械打的**，不一定等于客户的真实意图，所以分诊准确率（约 64%）我不用来调提示词。
- **评审和被评的模型同族**：交叉评审把这个代价量出来了（`major` 5.9% → 11.7%），逐条一致性只有中等（kappa 0.545）。所以回复质量的数字只能横向比较方案，不能当准确率用。
- `笼统消息` 的 40 条是我手写的，前 20 条和分诊提示词里的示例有重合，后 20 条是之后新写的、未出现在提示词里，两批结果都是 19/20 和 20/20 追问。
- **订单、物流、店铺是合成的沙箱数据**，不是真实系统；**角色靠请求头模拟，没有密码或令牌**，不能直接上线。审计表没有防篡改。
- 工具选择和注入评测的用例都是模板，比真实客户规整。
- **单次模型调用耗时随网关负载变化很大**：40 条串行实测整单 p50 6.01 s / p95 8.95 s，同一天另一次真实走查里单次调用 p50 7.7 s、最大 20 s。文档里的耗时数字对"网关繁忙"没有代表性，别当 SLA。
- ~~Docker 镜像没有构建过~~ **已构建并运行验证**（Docker Desktop 29.9.3，Linux 容器）：`docker build` 退出码 0，镜像 714 MB；容器以 `app` 用户启动、健康检查 `healthy`、`/health` 返回 `{"ok":true}`；`/app/data` 下由 app 用户创建 `tickets.sqlite` / `gateway.sqlite` / `checkpoints.sqlite` 和 `traces/`（那条按推理加的 chown **成立且必需**，删掉会 `PermissionError`）；无 `X-User-Id` 请求 `/tickets` 返回 401；`docker compose config` 解析通过。
- 构建侧的环境坑（不是项目问题）：国内直连 Docker Hub 超时，且 `# syntax=docker/dockerfile:1` 的 frontend 解析发生在 **buildx 客户端进程**里，不吃 daemon 的代理配置——必须给 `docker build` 命令本身设 `HTTP(S)_PROXY`。
- **并发只在网关这一层量过**：`eval/bench_gateway.py` 用的是假工具、单机、8 个进程，没有做端到端压测。延迟的分解已经量过（见上面「延迟」一节：模型 p50 6.01 s、本地 p50 1 ms），但那是串行单机的一次采样，不是容量结论。**trace 查看器已在无头浏览器里验过**（`uv run python scripts/check_viewer.py`：渲染 12 个 run，检查执行后的 DOM 里有没有详情面板；缺标记退出 1，找不到浏览器退出 2、不算通过）。点击切换 run 是在 Chromium 里手工点过一次，没有自动化。
- **MCP 通道没有认证**，身份由 `--user` 启动参数指定，连上来的客户端可以声称是任何人。只读工具在 MCP 上会直接执行；写操作拿不到批准，因为这条通道上没有人能批准。
- **MCP 只做了 server 方向**：本项目把工具暴露给别的 agent，反过来「用别人的 MCP 工具」还没接进规划节点（规划器的工具集是固定的五个只读工具）。
- 向量索引离线构建约 20 分钟（2.2 万个 chunk，CPU），本项目没有做增量更新。

## 开发过程

这个项目用多个 AI 编程 agent 协作完成（检索层、网关内核、工单存储、沙箱、可观测、评估脚本、查看器、测试等由不同 agent 在各自的 git worktree 里实现，我负责接口设计、验收、集成和真实数据上的评估）。`.team/` 保留了当时的协作规则和任务说明。

两点经验：
- **worker 自己的单测发现不了的问题，只有在真实数据和端到端运行里才暴露**：指标分母、引用被长编号误杀、槽位硬门槛、知识库乱码；治理阶段则是网关对不同调用者回放缓存结果、工具抛异常后被当成"没执行"而重复执行、审批永不过期、负数分页会倒出整张审计表、笼统消息被追问了错误的槽位。
- **让另一个 agent 只看接口、独立写攻击性测试**（网关的黑盒对抗测试）找到了作者自己测不到的 bug。其中一个 agent 的最终报告被网关内容审查拦截（提示词注入语料触发了敏感词），代码和测试由我另行验证后提交。
