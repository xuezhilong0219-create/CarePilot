# CarePilot：售后工单助手

面向电商 ERP（旺店通）售后技术支持场景的**工单 Agent**。不只是检索问答：它会查订单/物流/店铺授权/工单进度，对外发送和改状态必须经人工批准，所有动作过一个**没有模型参与判定的工具网关**（四道闸、审计、幂等、崩溃恢复、预算守卫），每次运行落一份节点级 trace，并有评估集度量每次改动的效果。

这是一个个人作品项目，**不是生产系统**：知识库是我做售后技术支持时用过的内部 wiki 导出；订单/物流/店铺是**合成的沙箱数据**；角色靠请求头模拟，**没有真正的认证**；评估集是 LLM 反向合成的。数字用来比较方案，不代表线上效果（见「局限」）。逐项对照功能清单的验收状态见 [docs/status.md](docs/status.md)。

技术栈：LangChain（模型与结构化输出）+ LangGraph（状态机、`interrupt` 人工审核、SQLite checkpoint）+ FastAPI（同步与 SSE 流式）+ SQLite（工单存储、网关账本与审计）。

## 它解决什么问题

最初我用某知识库产品的 API 做过一个客服问答，检索是黑盒，也不能执行动作。检索问答现在很常见，所以 CarePilot 把重心放在**让 Agent 敢动手**所需要的东西上：

- **模型只能提议，不能决定。**规划模型只看客户说过的话，只能提议只读查询；订单号必须逐字出现在客户消息里才会执行；写操作和对外发送只由确定性代码在人工批准后经网关执行。
- **越权和"不存在"不可区分。**查别家店铺的订单与查一个不存在的订单，回复逐字相同。
- **可以崩、可以重放。**幂等键、账本、对账：进程被强杀后恢复，副作用恰好一次。
- **能解释、能回溯。**每个动作进审计（含被拒绝的），每次运行一份节点级 trace，成本 = 实测 token × 你配置的单价。

## 工作流

```
工单 → classify（类别/严重度/实体/是否笼统，带上对话历史和之前累积的槽位）
        ├─ 笼统 ─────────────────→ 追问（通用："具体是什么问题"）
        ├─ 需查客户自己的数据 ───→ plan_tools：规划→只读工具（最多 4 步，守卫防死循环）
        │                           ├─ 查到 → 依据查询结果生成回复
        │                           ├─ 没查到/无权（回复逐字相同）/参数不对 → 追问
        │                           ├─ 物流接口超时 → 固定降级文案，不经模型
        │                           └─ 没有合适工具 → 升级
        └─ 其余 → 检索（客户说了版本就按产品线过滤）→ 生成回复（带结构化引用）
                          ├─ 能答且引用有效 → 草稿存为工单内部备注 → 人工审核
                          ├─ 答不了且缺信息 ─→ 追问
                          └─ 答不了 ─────────→ 路由到团队 → 人工审核 → 升级
人工审核 approve →（网关：批准）→ 客户看不到任何回复 →（二次确认）→ 发送，幂等；重复确认不产生第二条消息
升级 → 网关执行 escalate_ticket，写入原因和已完成动作 → /handoff 给下一个坐席
任意节点超预算/循环 → 只留内部备注并标 needs_human，不替人改状态
```

流程图和设计取舍见 [docs/architecture.md](docs/architecture.md)。

## 快速开始

```bash
uv sync
cp .env.example .env          # 填 LLM_API_KEY / LLM_BASE_URL（OpenAI 兼容网关）
uv run pytest -q              # 不需要网络和 key，用假模型
uv run uvicorn carepilot.api.app:app --port 8000
```

默认用仓库自带的**示例知识库**（`data/kb/`，合成数据，仅供演示和测试）。用真实知识库：

```bash
uv run python scripts/build_kb.py --raw <导出目录> --out data/kb_real   # 清洗，不调用 LLM，几秒
KB_DIR=data/kb_real uv run uvicorn carepilot.api.app:app --port 8000
```

服务默认是**治理模式**，所有接口需要 `X-User-Id` 头。演示用户（角色和店铺范围取自用户表，请求自报的角色无效）：客户 `c1`（店铺 S1、S2）、`c2`（S3）、`c3`（S4），坐席 `a1`、`a2`，管理员 `admin1`。

> **Windows 终端注意**：在 Git Bash / cmd 里用 `curl -d '含中文的 JSON'` 内联传中文时，请求体可能被终端按 GBK 编码，服务端会返回 `400 There was an error parsing the body`（服务端只接受 UTF-8，我用 GBK 编码的请求体复现过）。要么把 JSON 放进 UTF-8 文件用 `--data-binary @msg.json`，要么直接用 Python 的 `httpx`/`requests`。下面的示例在 Linux/macOS 终端可以直接用。

```bash
# 客户开单（示例知识库里答得出的问题）。status=awaiting_review 表示有草稿等坐席审核；need_info 表示系统在追问
curl -X POST localhost:8000/tickets -H 'X-User-Id: c1' -H 'content-type: application/json' \
  -d '{"message":"店铺授权过期了怎么办"}'
# 客户在同一张工单里继续说（历史和已识别的平台/店铺/功能会带进下一轮）
curl -X POST localhost:8000/tickets/T-000001/messages -H 'X-User-Id: c1' -H 'content-type: application/json' -d '{"message":"还是不行"}'
# 坐席审核：approve / edit（带 reply）/ reject。回复类工单默认两步：批准后客户仍收不到回复
curl -X POST localhost:8000/tickets/T-000001/review -H 'X-User-Id: a1' -H 'content-type: application/json' -d '{"action":"approve"}'
# 二次确认才真正发送（幂等：重复确认只发一条，工单置为 resolved）
curl -X POST localhost:8000/tickets/T-000001/confirm -H 'X-User-Id: a1'
# 交接摘要 / 审计 / 引用原文（只给坐席和管理员）
curl localhost:8000/tickets/T-000001/handoff -H 'X-User-Id: a2'
curl localhost:8000/tickets/T-000001/audit -H 'X-User-Id: a1'
# 流式：每个节点完成发一个 SSE 事件，最后一个 result 事件内容与同步响应一致
curl -N -X POST 'localhost:8000/tickets?stream=true' -H 'X-User-Id: c1' -H 'content-type: application/json' -d '{"message":"..."}'
```

审核卡有两种：**回复草稿**（`resolution=auto_reply`）的 `approve` 走"批准 → 二次确认 → 发送"；**升级卡**（`resolution=escalate`，知识库答不了或要查账单）的 `approve` 就是"确认升级"，直接执行 `escalate_ticket`，没有待确认的发送——这时再调 `/confirm` 返回 409 是正常的。后续轮次里系统判断资料不足也会把原来的回复草稿变成升级。

旧的"演示模式"（无身份、mock 工单系统）仍保留：`create_app(governed=False)`。

每次运行落一份 trace JSON 到 `data/traces/`，用 `uv run python scripts/trace_viewer.py --traces data/traces --out viewer.html` 生成可按节点展开的单文件查看器；成本报表见 `scripts/cost_report.py`（单价需要你自己填 `pricing.json`，不会替你编价格）。一键评测：`python eval/eval_all.py --quick`（本机没有 `make`；Makefile 只是转发）。

## 评估结果

评估集 279 条（可答 203：功能 146 / 平台对接 25 / 规则变更 19 / 仓库物流 13，其中 45 条带报错原文；需查数据 24；无关 12；笼统消息 40）。全部用 `deepseek-v4.1-flash-1017`，检索 BM25。

### 端到端：每次改动前后

| 版本 | 可答：放行且引用命中 | 需查数据→升级 | 笼统→追问 |
|---|---|---|---|
| 最初版本 | 98/203 = 48% | 23/24 | 8/40 = 20% |
| 修复引用校验 + 两层追问 | 164/203 = 81% | 22/24 | 40/40 |
| 再加：需查数据直接升级 | 169/203 = 83% | 24/24 | 39/40 |
| 再改：回复提示词禁止编造 | 159/203 = 78% | 24/24 | 39/40 |
| 接入工单存储/网关/工具后（同一代码**重复运行 4 次**） | 163~169/203 = **80.3%~83.3%**（均值 81.7%） | 24/24（4 次全部） | 39~40/40（2 次 40、2 次 39） |

最后一行看似比第三行低，是用一部分放行率换回复质量（见下表）。**同一份代码重复运行 4 次，"放行且引用命中"在 163~169 条之间波动（约 ±3 条）**，所以相邻两行相差几条不能当作结论，只有 48% → 80% 以上这种量级的变化才是真实的。可答样本被误拒的比例：4 次分别是 7.4%、5.4%、6.4%、7.4%，均 ≤10%。

### 回复质量（评审模型逐条核对"回复 vs 被引用资料原文"）

| | 具体事实无依据 | 仅无害多余内容 | 无编造 | 回复含内部资料编号 | 平均长度 |
|---|---|---|---|---|---|
| 修订提示词前（188 条） | 25.5% | 47.3% | 27.1% | 10.6% | 335 字 |
| 修订提示词后（183 条） | 5.5% | 3.8% | 90.7% | 0% | 138 字 |

**这是同一个模型评自己，存在自我偏好，数字偏乐观。**评审给出的"无依据"我抽查了 3 条对照原文，3 条都属实（编造了原文没有的操作步骤、把版本号安在了错误的功能上、说了原文没有的一列）。5.5% 说明剩余问题仍存在，没有解决。

### 检索（203 条可答，客户原话直接检索）

| 检索器 | hit@1 | hit@10 | chunk_hit@4 | 单次耗时 |
|---|---|---|---|---|
| BM25（默认） | 0.645 | 0.916 | 0.808 | <1 ms |
| 纯向量 bge-small-zh | 0.389 | 0.709 | 0.601 | 5 ms |
| 混合，等权重 | 0.552 | 0.916 | 0.837 | 6 ms |
| 混合，向量权重 0.25 | 0.621 | 0.926 | 0.857* | 10 ms |
| 混合 + bge-reranker-base | 0.606 | 0.931 | 0.867 | 5.4 s |

`chunk_hit@4`：回复节点实际只看到前 4 个 chunk，里面有标准答案的比例，最贴近线上。
\* 向量权重在 dev 半边（111 条）上调，在 test 半边（92 条）上 chunk_hit@4 为 0.848，BM25 为 0.804，**提升不显著**。端到端上混合检索没有更好（解决率 78% 对 83%，在噪声边缘），所以默认用 BM25：客户习惯贴报错原文、平台名、功能名，这种精确匹配 BM25 本来就强（带报错原文的样本 hit@10 达 0.98）。

### 治理层（逐项验收状态见 [docs/status.md](docs/status.md)）

| 度量 | 结果 | 怎么测的、要注意什么 |
|---|---|---|
| 工具选择（60 条模板） | 明确问法 52/52，参数 48/48，越权 6/6，泄露 0 | **标签在看到结果后改过**：第一次真实运行 53/60，7 个"错误"全是歧义问法（"看下发货了没"，查订单或查物流都说得通），之后改成两个工具都可接受并单独统计。所以明确问法的 52/52 不是独立准确率；越权和泄露的结果不受改标签影响 |
| 提示词注入（60 条 = 10 种载荷 × 5 个位置） | 被带偏 **0/60** | **去掉提示词里的防护行做对照也是 0/60**：防护行在这个模型上没有可测量的贡献，模型本身对这些模板化注入就稳。判分器已校准（顺从的回复必被检出）。注入文本会让 21/60 的回复直接拒答。结构性防护（回复节点无工具、写操作经网关）才是真正的防线，单测验证 |
| 产品线过滤（14 对企业版/极速版同名文档 × 2 方向） | 不过滤时混进另一产品线同名文档：**21.4%（纯标题问法）~42.9%（带套话问法）**；过滤后 0/28，没有挤出正确文档 | 过滤后的 0 在构造上基本是保证的（判定和过滤是同一个条件）；有信息量的是不过滤时的比例，但它随问法差一倍。LLM 出陷阱题基本行不通（9 个可区分配对只生成出 3 对），所以直接测检索+过滤 |
| 一键评测 `--quick`（60 条分层子集） | Recall@5 0.897，答对率 0.872（n=39），拒答准确率 1.000（n=21），误拒率 0.051，笼统追问率 1.000（n=10） | 5 分 37 秒；可答只有 39 条，波动比全量大；`--full` 没跑过 |
| 网关强杀恢复 | 真实子进程强杀，副作用前/后两个崩溃点恢复后副作用恰好 1 次 | Windows 的 `TerminateProcess`，不是 Linux 的 `kill -9`；没有做"整个 API 进程被杀后图的 checkpoint 恢复"的端到端测试 |
| 预算守卫 | 同一调用连续 3 次 → loop；乱换参数 → 20 步内 steps；超 token/耗时都能打断；被中止后只留内部备注并标 needs_human | 守卫在节点边界和规划循环里计数，**打断不了一个已经卡住的模型调用**（靠 HTTP 超时） |
| 成本 | 真实运行 8 次：prompt 9108 / completion 4501 tokens，`usage_missing` 0 次 | **没有金额**：网关价格接口返回模糊值，单价必须你自己填 `pricing.json`；没填只报 token |

## 局限（面试前要先讲清楚）

- **评估集是 LLM 用文档反向合成的**，问题用词天然偏近原文，BM25 的数字偏乐观。我抽查过一部分，没有逐条人工审核。真实工单上的表现需要真实数据验证。
- **每个样本只标了一个标准答案文档。**另一篇文档也能答对时，检索到它会被算作没命中。我同时报严格和宽松两档，只能缓解。
- **类别标签是按文档所在目录机械打的**，不一定等于客户的真实意图，所以分诊准确率（约 64%）我不用来调提示词。
- 评审和被评的是同一个模型。
- `笼统消息` 的 40 条是我手写的，前 20 条和分诊提示词里的示例有重合，后 20 条是之后新写的、未出现在提示词里，两批结果都是 19/20 和 20/20 追问。
- **订单、物流、店铺是合成的沙箱数据**，不是真实系统；**角色靠请求头模拟，没有密码或令牌**，不能直接上线。审计表没有防篡改。
- 同一个模型自己评自己（回复质量评审）；工具选择和注入评测的用例都是模板，比真实客户规整。
- **单次模型调用耗时随网关负载变化很大**：评估时整单约 3 秒，一次真实走查里单次调用 p50 7.7 秒、最大 20 秒。文档里的耗时数字对"网关繁忙"没有代表性。
- **未验证**：Docker 镜像没有构建过（本机没有 docker），只做了配置文件的语法检查；没有并发和压力测试；trace 查看器只做了静态检查和 XSS 载荷测试，没在真实浏览器里点过。
- 向量索引离线构建约 20 分钟（2.2 万个 chunk，CPU），本项目没有做增量更新。

## 项目结构

```
src/carepilot/
  graph/          状态、节点、路由（routing.py 建图与评估共用）、建图
  toolbox.py      把沙箱查询和工单操作注册成网关里的工具；规划→来源校验→执行
  gateway/        工具网关：四道闸、审计、幂等账本、批准/二次确认、崩溃对账、预算守卫（没有任何模型调用）
  store/          工单存储：状态机、SLA、三角色权限、可见性、交接摘要
  sandbox/        合成的订单/物流/店铺数据、脱敏、会超时降级的物流客户端
  observability/  节点级 trace、成本统计、节点包装层（trace 和守卫共用）
  viewer/         单文件 trace 查看器（XSS 加固）
  retrieval/      BM25（倒排）、向量、RRF 混合、重排、factory
  ingest/         知识库清洗（纯规则，确定性）
  evaluation/     指标、运行器、评估集生成、工具选择/注入评测
  api/            FastAPI：app.py（演示模式）、governed.py（治理模式）
  auth.py         角色与调用者身份（请求头模拟）
eval/             评估与实验脚本（真实评估集和报告在 eval/real，不入库）
scripts/          build_kb.py、build_index.py、cost_report.py、trace_viewer.py
docs/             架构、功能清单验收状态（status.md）、需求追踪、面试材料、记忆约定
tests/            约 610 个测试，均不依赖网络和真实数据（含真实子进程强杀、黑盒对抗、XSS 载荷）
```

## 开发过程

这个项目用多个 AI 编程 agent 协作完成（检索层、网关内核、工单存储、沙箱、可观测、评估脚本、查看器、测试等由不同 agent 在各自的 git worktree 里实现，我负责接口设计、验收、集成和真实数据上的评估）。`.team/` 保留了当时的协作规则和任务说明。

两点经验：
- **worker 自己的单测发现不了的问题，只有在真实数据和端到端运行里才暴露**：指标分母、引用被长编号误杀、槽位硬门槛、知识库乱码；治理阶段则是网关对不同调用者回放缓存结果、工具抛异常后被当成"没执行"而重复执行、审批永不过期、负数分页会倒出整张审计表、笼统消息被追问了错误的槽位。
- **让另一个 agent 只看接口、独立写攻击性测试**（网关的黑盒对抗测试）找到了作者自己测不到的 bug。其中一个 agent 的最终报告被网关内容审查拦截（提示词注入语料触发了敏感词），代码和测试由我另行验证后提交。
